LENS 3 — IMPLEMENTABILITY & INTERNAL COHERENCE review of I1_CANONICAL_METRIC_AND_EVENT_CONTRACT.md

**F1. BLOCKER — §4.2 (idempotency keys + reconciliation preamble): three key components are uncomputable from the named authorities, which also makes the promised backfill sweep unimplementable.**
- `state_change_seq` (saved/unsaved): never defined. `saved_vehicles` is a current-state table; a delete leaves no row and no counter. There is nothing to derive a monotonic per-(user,vin) sequence from, and a save→unsave→save cycle either collides keys or makes the key vacuously unique. Worse, the §4.2 preamble promises "a reconciliation sweep backfills" failed event inserts — but a missed `_unsaved` leaves zero trace in `saved_vehicles`, so the sweep cannot detect it, and even for detectable gaps it cannot recompute the same seq the inline path used (double-emit risk).
- `marketplace_price_changed` key `hash(vin, old, new, updated_at)`: `updated_at` is re-stamped on every write, so a retried request emits a fresh key → duplicate events (idempotency defeated exactly when needed). And `vehicles` stores only current price, so the sweep cannot reconstruct `old` for backfill.
- lifecycle key `hash(vin, from_status, to_status, transition_seq)`: `transition_seq` undefined; `vehicles.publication_status` is a single column with no transition ledger, so neither seq nor a missed transition is recoverable. A→B→A within one day is realistic (pause/unpause) and collides without a real seq.
- `marketplace_compare_added/_removed` key uses `action_seq` — undefined, and compare sets are typically client state, so the server cannot derive it; a client counter resets on crash/retry.
Fix: I2 must add (or name) durable anchors — a save/unsave audit row id, a price-history row id, a status-transition row id — and define each idempotency key as that authority row's id (as inquiry/reservation already correctly do). Drop `state_change_seq`/`transition_seq`/`updated_at` hashes. Scope the backfill promise to events whose authority retains a row; explicitly exclude (or re-anchor) delete-shaped events.

**F2. MAJOR — §3 `occurred_at` clamp vs §5.4 late-event rule: contradictory and lossy.** §3 clamps any occurred_at older than 24h forward to `received_at − 24h`, destroying the true timestamp. §5.4 then says events "later" than the clamp window are "stored, flagged, and excluded from certified windows" — but after clamping, no stored event is ever >24h old, and the only flag is `time_adjusted`, which is also set for small future-skew clamps that §5.4 says ARE included. So the certified-window exclusion has no distinguishing signal, and the information needed to compute true lateness is gone. Compounding: §3 lists `time_adjusted` in `exclusion_flags` "(§5.3)", but §5.3 does not list it, while §7 defaults say "exclusions = §5.3 full set" — engineers will disagree on whether time_adjusted events are excluded from all rollups. Fix: store raw `occurred_at_client` alongside the clamped value; split the flag into `clock_skew_adjusted` (included) vs `late_beyond_window` (excluded from certified windows); state explicitly which flags are in the rollup exclusion set.

**F3. MAJOR — §4.1 `marketplace_listing_opened`: server-emitted but keyed on client-minted values that may not exist at the GET.** Key = hash(session_key, listing_id, page_view_id), both C-fields. Unresolved: (a) SSR/first navigation, crawlers, curl, and API consumers send no page_view_id/session_key — is the event rejected (undercount), emitted with nulls (all such opens collapse into one key), or keyed differently? (b) a network-failure retry that the client wraps in a NEW page_view_id double-counts one human view, while the doc only covers the same-page_view_id retry; (c) SPA soft navigation — whether page_view_id rotates per route transition is unstated, and it directly moves the Views number; (d) "excluding declared prefetch" — the declaration mechanism (header? which?) is unspecified and differs per platform. Fix: define the no-client-context path (reject + counter, or server-fallback key), mandate page_view_id rotation semantics per navigation, and name the prefetch signal per platform.

**F4. MAJOR — §5.2 no-retroactive-merge silently guts the auth-crossing conversion metrics (§7 conv_view_inquiry, conv_view_save, attribution).** Views/impressions are mostly anonymous (actor_key = session_key); inquiries/reservations require auth (actor_key = user_id). With actor_key switching at login and no merge, the inquirer has no earlier-stage event under their actor_key, so "distinct actors at later stage who had earlier stage" trends toward zero for the dominant browse-anonymously-then-sign-up flow — a fake-low rate rendered as a confident `value`, the exact failure class §8 exists to prevent. The envelope already carries `pseudonymous_session_key` on authenticated events, so same-session (not retroactive) linkage is possible, but §5.2 as written forbids/omits it and two engineers will build this differently. Fix: either explicitly permit within-session (same session_key) stage-linking for funnel numerators while keeping distinct-actor_key denominators, or register the auth-boundary vacuity as a known defect with an `insufficient_data`-style guard — not just the "unique continuity" undercount note.

**F5. MAJOR — §7 conversion rows: "same-listing scoping" is undefined above the per-listing grain.** §7 defaults say metrics roll up "per listing/seller/tenant/platform", but for seller-level conv_view_inquiry there are two incompatible constructions: (a) sum per-listing (actor viewing 3 of the seller's listings inflates the denominator 3×, so it is no longer "distinct actors"); (b) distinct actors across the seller's listings (then an actor who viewed listing A and inquired on listing B breaks "same-listing" pairing — counted or not?). Fix: define rollup composition explicitly, e.g. seller-level = distinct actors with (view, inquiry) on the *same* listing anywhere in the seller's inventory / distinct actors with ≥1 view of any of the seller's listings — or declare conversion metrics listing-grain-only.

**F6. MAJOR — §7 `sales@1`: dual authority ("escrow_trust_sessions settled; `_sold` lifecycle transition") with no union/dedupe rule.** A settled escrow session and a `_sold` transition for the same vehicle can both occur (double count) or a cash sale may appear only as `_sold` (which source wins?). Uniqueness "session/vin id" mixes two id spaces. Fix: define sales = distinct VINs satisfying either condition in window, with the precedence and the dedupe key stated.

**F7. MAJOR — §4.1 search events: emission site is contradictory, and Lost Opportunity depends on it.** The section header says client-emitted/batched; `marketplace_search_performed`'s trigger says "actually executed server-side" and `_zero_results` is "server-emitted alongside". One engineer builds a client post-response emitter (lossy on abandon, can't be trusted for LO1's "listing field snapshot"), another builds it into the list API. Fix: declare both search events server-emitted in the list API (they need result_count and the normalized filter set anyway) and move them out of §4.1 or annotate the exception; state that the same request must also capture the LO1 snapshot inputs.

**F8. MAJOR — §7 `attribution@1` is internally incoherent.** "First-touch capture … persisted per actor" cannot yield "credit = last non-direct touch within 30 days" — last-non-direct requires persisting the full touch history, not the first touch. Additionally "per actor" collides with F4: the touch lands on the anonymous session_key, the conversion on the user_id, and with no merge the credit is unresolvable. Fix: specify a touch-history store (all validated touches, 30-day TTL, keyed so it survives login) and state which model (first vs last-non-direct) is the credited one per report.

**F9. MINOR — §4.2 table contains `marketplace_inquiry_started`, a client-emitted funnel event, under the "server-emitted in the same request as the domain write" header.** An implementer applying §4.2 semantics (server emission + reconciliation sweep) to it would be wrong. Fix: move the row to §4.1 or §4.3.

**F10. MINOR — terminology collision: "session".** §5.1's `pseudonymous_session_key` is a device/profile-lifetime key; §5.2 defines a *session* as 30-min-gap activity; §7 uniqueness cells say "per (session, listing, page_view)" meaning the key, not the 30-min session. Fix: rename the key `device_key`/`pseudo_actor_key` or the cells to "per (session_key, …)".

**F11. MINOR — §7 `views@1` note "supersedes nothing — no prior view metric existed" contradicts §4.6 "`marketplace_listing_viewed` is superseded by `marketplace_listing_opened`."** Both statements can't stand unqualified. Fix: reword the §7 note to "no prior *certified* view metric existed; the legacy referral-conditional event is superseded per §4.6 and never counted."

**F12. MINOR — §7 `watchlist_churn@1` "saves at window start" has no computable source named.** `saved_vehicles` is current-state (no historical snapshot); event-cumulative reconstruction only works after I3 launch and is distorted by any backfill gap (F1). Fix: define it as event-derived from ledger inception with the ledger-start boundary stated, or require an I4 daily snapshot of live save counts.

**F13. MINOR — §3 `tenant_id`/`organization_id` "derived from the object (listing's owning tenant)" is undefined for non-listing events** (searches, compare_viewed over multi-tenant sets, process steps). Null? Actor's tenant? Multi-valued? Fix: state per-type derivation (search → null/platform scope; compare → per-listing fan-out or null).

**F14. MINOR — §7 `price_response@1` underspecified on overlapping changes and ledger inception.** Two price changes within one window length: which anchors, and does the second's "before" window overlap the first's "after"? Before-windows predating the ledger produce a fake-low baseline. Fix: minimum spacing rule (else `insufficient_data`) and a ledger-inception guard.
